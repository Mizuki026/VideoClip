# 最终版第 5 窗口规格：共享限流与受控自动恢复

## 目标与基线

让新纳入的任务在共享模型冷却或可恢复执行故障后，先完成可信停止确认，再由持久化、有界的维护协调续接。所有续接复用冻结配置与匹配检查点；分析执行并发仍为 1，模型请求、自动恢复和第 4 窗口补投预算分别计数。

开始时分支 `codex/mvp`、HEAD `b606824`（父提交 `99340d5`），工作区干净；迁移文件链为 `b4c91e7a2d60` ← `f71a0d8c2e31`，没有切换分支或重置。第 4 窗口保留默认 8 次补投和 24 小时可推进期限；正常 execution、停止确认阻断、公平排队会暂停并顺延期限。本窗口不重置这些字段。

## 范围与非目标

- 在 PostgreSQL 按 `(provider, account_reference, model)` 保存共享冷却；账户引用是非秘密稳定标识。同账户更换 API key 不创建新额度。新增任务冻结账户引用；密钥轮换保持该引用，显式切换供应商账户时配置新的引用。未含该字段的历史冻结快照不改写，兼容时使用部署配置的账户引用。
- ASR 与 LLM 客户端通过受限 JSON 文件契约将稳定错误码、合法 `Retry-After` 原值及响应观测时间传回父 Worker；契约不得携带密钥、响应正文或诊断正文。
- 每个外部模型调用前在短事务中同时检查冷却并预留对应请求。事务在网络请求前结束。门禁阻断写入普通等待并退出 execution，不增加请求或失败预算。
- 实际请求返回 429 属于真实失败：保存共享冷却，已预留的 ASR / 总结额度不退还；失败须在 Stage 3 停止证据确认后才允许自动恢复。
- 等待任务保存原因、共享额度引用、单次截止、累计等待、下次检查和续接阶段。门禁重新检查当前冷却，冷却延长不可由旧定时记录绕过。冷却等待期间暂停第 4 窗口可推进期限，恢复排队时按原规则顺延期限并重新取得公平队列资格。
- 受控自动恢复仅接受显式白名单错误。每 task 最多 2 次；唯一自动操作在同一事务创建 child attempt 并计数。正常等待续接、重复扫描、重复消息和人工恢复不扣该预算。鉴权、模型配置、媒体、来源/指纹、结果校验、停止证明失败均不自动盲目重跑。
- 总结请求维持每 task 最多 3 次，跨全部 attempt 与人工/自动操作共享，开始前原子预留，任何预留后中断或失败不退还。自动恢复不为人工预留次数；在预算已满时不创建无效的 summary 恢复。
- 复用现有 Beat、`maintenance` Worker 和 `coordinate_analysis_delivery`。维护 Worker 只做有界扫描、资格事务和消息投递，不调用模型、不领取分析。单次扫描上界沿用 4 项。
- 页面显示等待阶段/原因/预计检查时间、停止确认状态、自动恢复次数、总结与补投预算。预计时间只代表下次检查，不代表请求或完成保证；不显示虚构的模型进度。

不实现媒体与笔记分离删除，不扩大 Stage 3 停止证明，不改变 ACK 策略，不制作最终展示材料，不调用供应商制造额度耗尽，也不启用付费模型兜底。

## 限流契约与参数

SiliconFlow 官方说明 429 可能由请求、token 等多项速率指标触发，限额主体为账户而非 API key，且限制按模型分别设置；官方建议 429 指数退避。实现以供应商/非秘密账户引用/模型作键。官方文档未承诺每个响应都提供 `Retry-After`，因此有合法字段时遵循字段，没有或字段非法时使用本地退避。HTTP `Retry-After` 按 RFC 9110 §10.2.3 接受非负整数秒或 HTTP-date。

| 参数 | 默认 | 允许范围 | 语义 |
| --- | ---: | ---: | --- |
| `SILICONFLOW_ACCOUNT_REFERENCE` | `primary` | 1–64 个字母、数字、点、下划线或短横线 | 同一账户和所有轮换密钥保持相同值；不得放入 API key。 |
| `MODEL_COOLDOWN_BACKOFF_BASE_SECONDS` | 60 秒 | 1–3,600 | 缺少/非法 Retry-After 时指数退避基数。 |
| `MODEL_COOLDOWN_BACKOFF_MAX_SECONDS` | 900 秒 | 60–86,400，且不小于基数 | 本地退避封顶；不截短供应商合法 Retry-After。 |
| `MODEL_WAIT_SINGLE_LIMIT_SECONDS` | 86,400 秒 | 60–604,800 | 单次等待的本地上限；供应商截止超过上限时转人工，保留完整共享冷却。 |
| `MODEL_WAIT_TOTAL_LIMIT_SECONDS` | 259,200 秒 | 60–604,800 | task 生命周期内累计等待上限；进程/服务重启和新 attempt 均不清零。 |

缺省退避采用 `nominal=min(max, base × 2^(n-1))` 的 equal-jitter 区间 `[ceil(nominal/2), nominal]`；纯函数显式接收 UTC `now` 和 `[0,1]` 随机分位数。429 更新以行锁和同一事务增加连续失败数并写 `max(当前截止, 新截止)`，并发较短建议不能缩短已有冷却。成功请求仅在其开始时间已晚于当前截止时重置连续失败数，不清除尚有效冷却。

对累计上限的计时只覆盖持久化的正常模型等待；停止确认完成前不创建 child attempt。重复扫描不重置等待起点。单次或累计本地期限到达时将任务转为需人工处理，不把模型冷却截短为可提前调用的时间。所有时间比较使用 UTC aware datetime；等待截止与累计值保存在数据库，Beat 重启不改变它们。

## 阶段续接与统一资格操作

task 使用 `waiting_model` 状态，attempt 使用同名状态表示正常门禁等待；task 保存 `transcribing` 或 `summarizing` 续接阶段、wait origin、provider/account/model、等待起点/截止及累计秒数。状态不是停止证明：维护扫描和后继 attempt 创建还必须核对精确当前 attempt/execution 绑定及 `stop_confirmed_at`。

- ASR 门禁通过后，才将片段 `request_count` 从 0 预留为 1；被冷却门禁阻断不修改片段请求行。续接以 full execution 重新提取并生成 manifest，只复用 `checkpoint_matches` 认可的成功片段。
- 总结门禁通过后，才插入 `SummaryRequest(started)`；被门禁阻断不消耗总结请求预算。完整转写续接使用 summary-only，并在创建时验证来源、manifest、transcript 和请求指纹。总结结构/引用校验修复是同 attempt 的有限请求循环，与执行失败后的恢复 attempt 分离。
- 自动恢复、人工恢复、等待续接调用同一事务生命周期函数。函数锁定 video/task/parent，检查删除状态、当前绑定、停止证据、指纹、总结预算、第 4 窗口预算、冷却和全局未确认 execution，再幂等创建唯一 child。恢复次数只在自动恢复接受并创建 child 的同一事务增加。
- 冷却等待到期后必须重新读当前共享冷却。若冷却被延长且仍在本地期限内，更新时间并继续等待；不创建 attempt。若冷却已解除，则使用实际续接阶段创建子 attempt、写新的 `queue_entered_at` 并清除当前等待字段，但保留 task 级累计等待和所有其他预算。
- 自动恢复资格只来自维护中的稳定白名单：受控 execution 被 Stage 3 可信停止确认判定为 `WORKER_EXECUTION_INTERRUPTED`，以及 ASR/LLM 的网络、超时、可恢复上游 5xx/过载和 429。输入拒绝、鉴权/权限、模型不存在/不兼容、源视频丢失、非法媒体、来源/manifest 失配、summary 输出/引用校验失败、数据库状态损坏、未知内部异常均不自动恢复。
- 自动候选扫描只取 due、仍为当前 task、停止已确认且未超预算的项目；等待中的任务不进入 queued 可执行队首。恢复、人工操作、删除取消或维护扫描竞争由相同 video/task 锁和唯一父子关系串行化。

若恢复额度耗尽、总结请求已达 3 次、投递重试/期限已耗尽、来源验证失败或无法确认旧 execution 停止，不创建无效 child。请求返回后而检查点/发布事务提交前中断仍可能让供应商看到重复请求；系统不承诺供应商恰好一次或费用恰好一次。

## 迁移与历史策略

迁移只添加本窗口必要的 nullable task 状态/预算/等待字段、共享冷却表、等待扫描索引和总结修复上下文字段，不给历史行伪造账户、计数、deadline、冻结快照或停止身份。新任务在提交时显式初始化独立预算。既有 `failed` / `awaiting_summary` 不参与自动扫描；用户在部署后显式发起并被接受的人工恢复/总结续接可一次性登记 Stage 5 纳入时间和新预算，过去 attempt 不计作新的自动恢复。历史快照保持不变；旧快照的限流键使用当前部署账户引用并在 UI/日志中标为部署兼容路径。

## 验收标准

1. 纯函数/事务测试覆盖共享账户引用、密钥轮换键稳定、秒数与 HTTP-date、非法字段 fallback、抖动端点、冷却只延长、并发预留、单次/累计期限及三种独立预算。
2. 客户端子进程集成覆盖 ASR 与 LLM 的 429 错误契约和 Retry-After 传递、网络超时、5xx、永久错误及不泄漏密钥/响应正文。
3. 隔离真实 Beat→Redis→maintenance Worker→analysis Worker 链路使用生产模型客户端与本地替身：共享 LLM 冷却阻止另一 task 的 LLM 而允许其 ASR；解除后任务自动续接、完整转写不重做、合法总结最多发布一次、全局最多一个未确认 execution。
4. 多轮调用前等待不消耗总结/恢复预算；实际失败自动恢复最多 2 次，总结请求跨 attempt 最多 3 次；分别覆盖 Stage 4 8 次/24 小时语义未被冷却等待误扣或重置，以及模型单次/累计等待耗尽。
5. 真实受控执行故障与强杀、DB 断连、停止确认写库失败、监督器死亡、迟到确认/结果证明：未取得 Stage 3 可信停止证据时不接管；确认后才可创建 successor。
6. 覆盖双扫描、自动/人工竞争、冷却延长、恢复创建后发送前崩溃、请求预留后中断、删除取消、指纹失配及重复消息，证明事务幂等和预算不重置。
7. 运行后端相关/全量测试、Stage 0 回归、Ruff、mypy、pip check、迁移与 Compose 检查、前端 lint/单测/build、真实浏览器等待/恢复，以及第 2–4 窗口安全与活性回归。故障只用隔离数据库/文件/Compose 与本地替身；不声称实测供应商账务。

## 官方契约依据

- SiliconFlow [Rate Limits](https://docs.siliconflow.cn/docs/userguide/faqs/rate-limit-and-upgradation)：账户级而非 key 级，模型独立配额，429 建议指数退避。
- SiliconFlow [Error Handling](https://docs.siliconflow.cn/en/faqs/error-code)：429 限流；503/504 可为服务负载问题。
- IETF [RFC 9110 §10.2.3 Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)：允许 HTTP-date 或非负十进制秒数。
