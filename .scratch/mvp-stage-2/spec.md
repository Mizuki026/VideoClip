本窗口是第 2 窗口“第一条异步转写链路”，对应技术方案“可恢复分析”阶段的前半段。窗口编号与技术方案阶段编号不同：本窗口先建立安全的提交、投递、单 Worker、真实 ASR 和持久化检查点；人工重试和检查点复用的用户流程在第 3 窗口，正式 LLM 总结及引用发布在第 4 窗口。产品与技术文档中已确认取消上传视频字节上限及业务目录运行期 5 GiB 容量限制；保留媒体时长、E 盘数据位置、单分析执行、有限期限及 Docker 新增占用 7 GiB 预算。

本窗口目标：

让已登录用户对已上传视频提交一次分析尝试，API 持久化投递事实，单个 Celery Worker 安全领取后按冻结配置逐片调用真实 ASR 并保存可查询的完整片段清单与成功检查点；整个过程在重复消息、停止和失败时不产生过期写入，也不把仅完成转写宣称为完整分析成功。

范围：

1. 在现有 FastAPI、PostgreSQL、Alembic、受控文件存储及本项目 Compose 上扩展，增加 Redis 与一个 Celery Worker，明确 API / Worker 共用业务规则和镜像、Redis 只传任务编号。Redis 持久化和任务工作目录位于 E:\VideoClip\data 下本项目受控路径；为新增依赖锁定经验证的版本，保留第 1 窗口业务库、API 配置与端口。修改本项目容器前先核对运行状态和数据归属；仅使用本项目限定的启停、迁移与恢复步骤，不操作其他项目。
2. 实现按视频行锁的任务提交：校验会话、所属用户、视频未删除、无当前活动任务及无停止未确认的旧执行；同一短事务持久化新的 task/attempt、不可变处理配置、`pending` 投递记录和视频当前任务关联，并将现有 `Video.analysis_task_created_at` 从 NULL 置为非 NULL。删除与提交竞争时只能有一个操作成立；已存在活动尝试的重复提交返回原任务。数据库提交后才尝试向 Redis 投递，HTTP 返回 202 和任务编号、分析状态及投递状态。
3. 分开保存分析状态、投递状态、执行停止事实及清理状态。投递记录区分 `pending`、`sent`、`unknown`、`failed`；发送异常只能改变经证实的投递事实，不能覆盖已经领取的执行状态。任务查询和转写读取接口供所属用户读取队列、执行阶段、已提交片段数、已保存文本、完整性、失败原因及后续恢复所需事实；跨账号不可见。第 1 窗口应用现有路由为 `/videos`，技术方案的部署接口写作 `/api/videos`；新增路由先保持现有客户端兼容，并记录同源代理如何映射 `/api` 前缀，不因本窗口扩展静默改名既有接口。`sent` 不等于任务已经执行，也不等于 Redis 中消息永不丢失。
4. 创建单 Worker 首次领取的条件事务和全局执行占位：部署内固定键的 PostgreSQL 会话级 advisory lock 使用专用连接持有，直到本地 HTTP 请求、写入者与媒体子进程确认停止；另有数据库约束保护停止未确认的执行记录。每个 attempt 最多一次首次领取并生成执行标识，所有阶段、清单、检查点及结果写入校验视频未删除、当前 task、当前执行标识和运行资格。重复、迟到或失效消息不得产生新模型/文件副作用；丢锁与 Worker 崩溃不能仅凭锁释放、心跳过期或 PID 缺失判定旧执行已停止。
5. 按冻结源文件身份、音轨、切片/时间轴版本、音频规格、ASR 模型及参数、总结模型/提示词与结构版本、期限及输出上限生成配置快照；密钥只按私密配置引用。对源文件、转写清单和单次 ASR 请求形成带版本的确定性指纹，供后续窗口判断检查点复用。默认配置改变不能修改已有任务快照。状态转换、错误分类、指纹和时间映射计算尽量保持纯函数；网络、文件与事务副作用留在业务操作和适配器内。
6. FFmpeg 在受控 attempt 工作目录提取 16 kHz、单声道、16-bit PCM 音频，约每 30 秒切片；先持久化完整预期清单、音频/原视频区间及映射版本，再顺序调用经第 0 窗口验证且当前账号仍可免费使用的 ASR。每片结果通过带执行标识的短事务单独提交；最后一片保存实际长度。原视频和已成功的转写记录保留。外部模型已返回而本地检查点未提交时不能声称已成功或保证外部调用恰好一次。
7. 为 FFmpeg、HTTP、数据库锁等待及整个 attempt 设置有限总期限和响应/诊断上限；超时、视频失效或丢锁时停止新增调用并有界终止所属进程组，确认退出后再记录停止回执、释放全局执行占位并回收可清理的临时文件。视频失效可在隔离测试中受控模拟，本窗口仍不得开放已提交任务视频的删除入口。无法确认退出时保留占位及清理路径，提供本项目限定的停止核验和登记步骤；本窗口不据此自动接管旧 attempt，也不实现创建新 attempt 的人工恢复入口。
8. 转写全部完成时持久化可查询的“待总结”事实，明确区别分析进度与当前执行者是否仍在运行；只有合法总结发布后才能将分析任务标为 `succeeded`。本窗口不调用 LLM，不生成假总结，也不把真实 ASR 成功或测试替身成功当作完整分析成功。若现有状态/阶段不足以准确表达“转写完成且执行者已停止”，以最小兼容变更补足状态、迁移、文档和测试，并留下后续第 3/4 窗口从冻结配置及检查点继续的明确接点。
9. 保存本窗口的运行命令、版本、单 Worker 配置、故障注入、真实 ASR 结果、停止证据及局限至 .scratch/mvp-stage-2/validation.md；完成有意义阶段后更新产品文档的阶段状态与现有技术方案的当前进度、限制和下一步。第 1 窗口 API / PostgreSQL 可能仍在运行，验证时保持业务数据、账户和已有视频可用；测试使用独立数据库及明确隔离的目录。

非目标：

- 不实现用户可操作的人工重试、自动重新投递、自动 Outbox 发布器、Scheduler、租约过期自动接管或 ASR 失败自动重跑；这些属于后续恢复窗口或 MVP 范围之外。
- 不实现正式 LLM 总结、引用结构校验/修复、分析成功发布、完整结果页面或 React 前端；测试替身只能证明本阶段控制流，不能对用户宣称完整分析成功。
- 不改变第 1 窗口账户、上传、媒体白名单与鉴权文件读取契约；不绕过 `analysis_task_created_at` 删除门闩来删除已提交任务的视频。已提交任务的视频删除需联动停止确认，留待后续窗口。
- 不恢复 1 GiB 单文件限制、业务数据目录 5 GiB 运行期硬限制或容量准入；不迁移/清理其他 Docker 项目，不把第 0 窗口探针脚本直接当作正式业务 Worker。

验收：

1. 真实 PostgreSQL 与 Redis/Celery 集成中，登录用户沿用第 1 窗口路由约定，对自己的视频 `POST /videos/{id}/tasks` 得到 202；任务、冻结快照、视频删除门闩和 `pending` 投递事实同事务成立。另一账号被拒绝；重复提交不产生第二个活动 attempt；与删除并发仅允许符合事务顺序的一方成功。查询只向所有者展示分析与投递状态，部署层 `/api` 映射策略有记录且不破坏已有路由。
2. 使用已授权视频通过真实 API → Redis → 单 Worker → FFmpeg → 真实 ASR → PostgreSQL 跑通顺序转写，预期清单及每个成功片段分别持久化；重启 API/Worker 后可查询准确的片段数、文本和原视频时间区间。已完成转写显示待总结，不返回 `succeeded` 或不存在的摘要。记录模型、配置/指纹版本、请求次数、耗时和调用证据；受控假 ASR 仅用于确定性故障测试。
3. 隔离测试覆盖“数据库提交后发送前退出”“发送成功但确认丢失”“重复、乱序及迟到消息”“同一 attempt 重复领取”“模型返回后检查点提交失败”。`pending/unknown` 不被误报为执行失败，已领取任务不被投递错误覆盖，同一 attempt 不重复调用模型，旧标识不能写入当前任务。手动恢复尚未提供时，异常状态和受限原因必须可查询，不能暗中自动重跑或误宣称恢复可用。
4. 隔离测试覆盖两个视频竞争全局执行权、FFmpeg 挂起、ASR 持续缓慢响应、受控模拟的视频失效及数据库会话/锁丢失。正常完成或可确认的本地失败释放执行占位；无法取得对应进程/请求停止确认时阻止新执行和文件回收，旧结果不能发布。停止核验只针对本项目 Worker 和子进程，测试不能以会话断开或心跳超时替代停止证据。
5. 证实工作目录、PostgreSQL 和 Redis 持久化位于本项目 E 盘业务目录；进程停止确认前不清理 attempt 文件，已保存转写不因临时音频清理而丢失。Celery 仅一个 Worker 实例、并发 1、预取 1，`acks_late=False`、`reject_on_worker_lost=False`、`publish_retry=False`，不启用业务 `autoretry`/`retry()`；相关确认与重复消息行为按实际锁定版本验证。
6. 运行直接相关单元及集成测试、全部适用后端测试、第 0/1 窗口回归、lint、类型检查、迁移、依赖和 Compose 配置检查。构建/运行新服务后核对本项目 Docker 新增镜像、缓存、可写层和日志与原预算的总量，不超过 7 GiB；原有 Docker 项目状态不变。仅报告实际运行命令、结果及未覆盖的限制。
7. 交付可复现的异步转写闭环、数据库迁移、配置与维护说明、.scratch/mvp-stage-2/validation.md、必要的技术进度更新和逻辑提交哈希。结论只能是“第 2 窗口异步转写阶段通过”，明确人工恢复、正式总结及用户完整成功结果仍待后续窗口，不能宣称 MVP 分析功能已完成。
