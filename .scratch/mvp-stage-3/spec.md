本窗口是第 3 窗口“人工恢复与故障处理”，对应技术方案“可恢复分析”阶段的剩余部分。第 2 窗口已有真实 API → Redis → 单 Worker → FFmpeg → ASR → PostgreSQL 链路，授权样片 13/13 片段已保存，任务处于 `awaiting_summary`，执行停止已确认；这不是完整分析成功。现有业务代码只允许首次提交，已提交任务的视频删除仍被门闩拒绝。产品决策已取消上传视频 1 GiB 字节上限及业务目录 5 GiB 运行期硬限额；仍保留 0～20 分钟媒体时长、E 盘持久化、单分析执行、有限期限及 Docker 新增占用 7 GiB 预算。

本窗口目标：

让用户在异步转写投递异常、执行失败或中断后，能依据可信的停止事实手动创建一次安全的恢复 attempt，仅补跑未成功的片段；并能安全删除已提交分析任务的视频或重试遗留清理。恢复、删除和迟到消息并发时，旧执行者不得重新调用模型、覆盖新检查点或阻止已完成的删除。

范围：

1. 在现有任务生命周期、存储与 API 约定上补齐恢复资格：区分未领取的 `pending` / `unknown` / 明确失败投递、已发送但久未领取、已领取后失败或中断、停止未确认，以及已完成转写的 `awaiting_summary`。排队时长只是提醒，不是消息丢失或执行停止的证明。任务查询向所有者返回稳定错误码、恢复资格及必要的投递、执行停止和清理事实；另一账号不可推断资源存在。不得将 `awaiting_summary` 当作失败重跑或 `succeeded`。
2. 提供与现有 `/videos/{id}/tasks` 兼容的显式手动恢复操作，请求携带原 task/attempt 身份并校验会话、CSRF、所有权、视频有效性及恢复资格。与 Worker 首次领取及删除使用同一视频行锁。未领取的原 attempt 可在同一事务原子失效；已领取的 attempt 即使已失败、超时或 advisory lock 已释放，也必须有相应执行者及其 HTTP 请求、写入者、媒体子进程的停止确认。无法证明停止时保持占位并提示本项目限定的人工停止核验步骤，不自动接管。恢复沿用原冻结配置，创建新的 attempt、独立工作目录及 `pending` 投递记录；重复请求同一父 attempt 只能得到同一子 attempt，后续再次恢复应以当前失败的子 attempt 为父。当前 schema 对视频仅允许一个 task；优先在同一个 task 下增加 attempt，若必须改变模型，先说明迁移和兼容影响，再以测试证明。旧 attempt 的状态与父子来源必须可审计。
3. 检查并修正现有 Celery 消息仅携带 task ID 的契约：同一 task 创建新 attempt 后，迟到的旧消息绝不能领取新 attempt。投递消息和领取条件必须绑定具体 attempt 身份或等价不可变代次；迁移前已经排队的旧格式消息应安全拒绝，不能猜测它属于当前 attempt。发布确认仍只更新对应投递事实；失败或不确定发送不覆盖已经领取的执行状态。不加入自动 Outbox 发布、自动重试或租约超时接管。
4. 新 attempt 重新验证源文件身份，按冻结音轨、音频、切片和 ASR 配置生成预期清单；只有片序、时间映射、音频内容/请求指纹及清单版本均匹配的已提交成功片段才可复用，并保留原片段来源供审计。只对缺失、失败或无法复用的片段发起 ASR；全片成功后仍停在 `awaiting_summary`。旧 attempt 的文本和临时文件不能被新 attempt 覆盖，已删除的旧临时音频可安全重建。外部 ASR 已返回但检查点提交失败时允许补调，不承诺供应商侧恰好一次。冻结配置或源文件无法兼容时给出明确错误，不能静默复用或退回当前默认配置。
5. 将已提交任务的视频删除纳入现有受控删除流程。接受请求时先在短事务锁视频、记录删除/清理意图并使当前 attempt 失效，再返回 `202` 或继续执行文件回收；从删除生效起拒绝新的内容、转写、任务恢复与媒体读取，只向所属用户提供删除进度。未领取的消息迟到时跳过；已领取执行按停止协议退出，停止未确认前不删除其工作目录、原视频或关联数据。确认停止后，可重入地清理 attempt 临时文件、原视频及关联转写、任务和上传记录；文件失败保留路径与错误，重复删除或启动检查可继续，只有全部清理完成才报告删除完成。不要用 API 进程后台任务代替删除状态的同步持久化，也不要绕过第 1 窗口原有上传租约与文件路径防护。
6. 提供单独的临时清理重试操作，针对已确认停止的 attempt 回收遗留工作文件，保留原视频和已持久化成功的转写；它不新建 attempt、不投递消息、不调用模型。启动检查可以处理已有且可证明无人使用的清理意图，但不能以 API/Worker 重启、PID 缺失或锁空闲作为停止证据。保留第 2 窗口本项目限定的 stop-and-confirm / cleanup 维护路径，并按实际执行 ID 使用；不得照搬验收记录中的历史 ID，不停止其他 Docker 项目。
7. 对状态迁移、恢复资格、检查点匹配和错误分类使用可独立测试的函数；持久化状态、文件删除和模型调用留在明确的事务/适配器边界。现有迁移、外部 API、消息与配置调用方同步更新。验证第 1 窗口未分析视频删除仍可用；Stage 1 与 Stage 2 现有服务和数据保持可用。把本窗口实际运行步骤、故障注入、停止证据、请求次数、失败案例及限制记录在 .scratch/mvp-stage-3/validation.md，并在完成有意义阶段后更新既有产品与技术进度。

非目标：

- 不实现正式 LLM 总结、引用结构校验与修复、分析 `succeeded` 发布；现有 13/13 的 `awaiting_summary` 继续等待第 4 窗口，不为了展示“成功”补一个空摘要。
- 不实现 React 三页面、播放器引用跳转、同源 `/api` 代理；保持当前实际 `/videos` 路由兼容，记录未来代理剥除 `/api` 前缀的约定。
- 不实现自动重试、自动接管停止未确认的 Worker、定时重投、全自动 Outbox 发布器或跨项目容器清理；不恢复上传字节上限、业务目录容量硬限制和水位拒绝测试。
- 不因第 3 窗口需求重做账户、上传或真实 ASR 适配器；只改安全恢复与删除所必需的调用方和契约。

验收：

1. 在隔离 PostgreSQL、Redis 和文件目录的测试中，覆盖 `pending` 未发、`unknown` 送达不明、明确发送失败、`sent` 久未领取、领取/恢复竞争、已领取失败但停止未确认、确认停止后的恢复。恢复事务一次只产生一个新 attempt；同一父 attempt 重放返回同一子 attempt；旧消息、旧执行标识和旧进程均不能领取新 attempt、调用 ASR 或写新检查点。并发删除与恢复只允许一个与事务顺序一致的结果。
2. 用至少两片的受控故障样本证明第 N 片失败后恢复：之前成功片段的文本、时间区间、指纹及来源一致，ASR 调用数不增加；只补发缺失片段，重启 API/Worker 后仍可读完整转写且状态仍为 `awaiting_summary`。对不匹配源文件、切片或请求指纹拒绝错误复用；记录模型已响应但数据库未提交片段可能重调的边界。第 2 窗口现有 13/13 记录仍可读、仍未成为分析成功。
3. 用受控慢 ASR/媒体子进程与真实停止核验，证明停止未确认时恢复和文件回收均被阻止；本项目 Worker 及所属进程退出并登记对应证据后才可继续。删除中立即禁止新请求读取内容与转写；清理失败显示进度和稳定错误，单独清理重试只做文件操作且不增加模型调用。测试未分析视频删除、已排队视频删除、正在执行视频删除、转写完成视频删除、重复删除、启动恢复及跨账号不可见。
4. 在本项目限定的运行环境完成一条可复现的真实 API → Worker → ASR → 故障 → 人工恢复闭环，核对真实请求/检查点与复用计数；故障注入须受控且不得污染第 2 窗口已有授权样片结果或业务库。测试替身用于竞态与失败确定性验证，不能代替真实链路验收；若外部免费模型当时不可用，准确记录阻塞及已完成的隔离验证，不声称真实闭环通过。
5. 先运行直接相关测试，再运行完整适用后端测试、第 0 窗口回归、Ruff 格式与 lint、Mypy、依赖、迁移和 Compose 配置检查；有新镜像/容器时核对本项目新增 Docker 镜像、构建缓存、可写层和日志总预算低于 7 GiB，并核对 Stage 1/2 服务及数据未受损。只报告实际运行的命令与结果，现有无关警告单独说明。
