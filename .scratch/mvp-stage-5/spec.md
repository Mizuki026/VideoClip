本窗口是第 5 窗口“页面闭环”，承接已验收的账户/上传、异步转写、人工恢复、安全删除与正式总结后端。第 4 窗口已有一条真实授权样本的 `succeeded` task、5 章、5 个知识要点及 10 条经原文和时间区间校验的引用；两条较早 `awaiting_summary` task 因历史清单指纹不匹配保留原状，不能在页面中伪装为可继续总结。当前仓库没有 React 前端或同源 `/api` 代理。业务范围继续取消上传文件 1 GiB 字节上限和业务目录 5 GiB 运行期硬额；仍保留 0～20 分钟时长、E 盘数据位置、单分析执行和 Docker 新增占用 7 GiB 预算。

本窗口目标：

让用户在同一浏览器源下完成注册/登录、原始视频上传、提交与查看分析、必要的手动恢复或清理、阅读转写和合法总结、点击引用跳转到鉴权视频对应片段，以及整条记录删除；刷新或重启服务后仍能按真实后端状态继续操作，不能把等待、失败、清理中或删除中显示为成功。

范围：

1. 在仓库内建立简洁可维护的 React + TypeScript 前端及锁定依赖，按产品设计实现注册/登录、视频列表、视频详情三个页面。使用清晰的中文状态文案、合理的空状态/加载/失败提示、可访问的表单与键盘操作，适配常见桌面和窄屏浏览器。UI 与 API 类型边界按实际响应定义，不在组件里复制后端状态机；界面所需的映射、轮询判断和时间格式化尽量用可单测的函数。先完成主要信息流，不因样式打磨扩展成独立设计系统。
2. 提供一个可复现的本地同源入口，使浏览器访问页面与 `/api/...` 时使用同一 scheme、host、port；代理剥除 `/api` 前缀后转发到现有 `/auth`、`/videos` 等后端路由，不复制或重命名业务接口。开发模式和构建后的本地演示模式都必须可用，代理对原始上传请求体、Cookie/Set-Cookie、HEAD、Range、206/416、流式响应和错误状态保持透明，不能先把大视频读入内存。后端 `APP_ORIGIN` 必须匹配浏览器实际源；若调整配置或端口，同步检查现有启动/验收脚本的调用方和 Stage 1/2 健康，不允许因代理引入跨源 CSRF 绕过或破坏原 API 客户端。
3. 前端会话只使用服务端 HttpOnly Cookie。通过 `/api/auth/csrf` 获取 token，所有状态变更请求携带 `X-CSRF-Token`，由浏览器自然发送精确 Origin；登录后通过 `/api/auth/me` 恢复身份，退出后清除页面中的用户数据并停止轮询/播放。不要把会话令牌、CSRF、转写或总结存入 localStorage、URL、普通日志或错误监控。未登录、会话到期、403 CSRF 失败及网络中断要给出可操作反馈；另一账号的资源不可见。
4. 上传使用后端已实现的 `POST /videos` 原始请求体契约：浏览器发送文件本身及 `X-Video-Filename`，不得改为 multipart/form-data、base64、整文件 ArrayBuffer 或分片上传。展示实际已发送字节和可计算时的进度；无法得知总量时显示不确定进度，不虚构百分比。支持取消并告知中断后需重新上传；服务端媒体拒绝、时长超限和文件 I/O 失败如实展示。不在 UI 增加 1 GiB 文件门槛、5 GiB 容量准入或浏览器侧整视频预加载。
5. 视频列表显示每条视频的可用/删除状态、基本元数据及入口；详情展示所属视频、任务投递/执行/停止/清理状态、已转写片段和进度、合法总结的章节/知识点与引用。当前 `GET /videos/{id}` 只有 `analysis_task_exists` 而没有当前 task ID；补充一个最小、向后兼容、仅所属用户可读的任务关联字段或查询接口，使刷新、深链和浏览器重启后能找回同一 task，不依赖会丢失的前端内存状态。前端根据后端 `status`、`stage`、`summary_status`、`delivery_status`、`recovery_eligible`、`recovery_error_code` 等真实事实渲染，不从排队时间或模型耗时推测执行停止，也不显示虚构进度百分比。
6. 处理中的 task 约每 2 秒查询一次，终态或需人工操作时停止对应分析轮询；页面不可见时降低不必要请求，回到页面后立即重新读取。对待总结、总结中、总结失败、已成功、清理失败、删除中分别提供准确的状态与动作。人工恢复使用后端 `/videos/{id}/tasks/{task_id}/recover` 及当前父 `attempt_id`；待总结续接使用 `/summarize`，清理重试使用 `/videos/{id}/cleanup` 及指定 attempt；按钮在请求期间禁用重复提交，并以 API 返回的实际状态刷新。两条旧 `awaiting_summary` 的 `TRANSCRIPT_SOURCE_MISMATCH` 应解释为历史来源校验未通过，保留记录且不循环重试或改写数据。停止未确认只能显示本项目限定的维护提示，不能让浏览器假装确认 Worker 已退出。
7. 使用原生 `<video>`，`src` 直指同源 `/api/videos/{id}/content`，让浏览器凭会话 Cookie 自行发 Range 请求；不得下载完整视频到 Blob 后播放。点击转写片段或总结引用时，等待必要的媒体元数据/可寻址状态，将 `currentTime` 设为后端返回的原视频 `video_start`，调用 `play()` 并处理播放拒绝或加载失败。展示引用原文与片段级起止时间，避免宣称词级定位。视频删除或登出后立即停止播放器并拒绝新的内容请求；已经发出的字节无法撤回，以后端新请求鉴权为准。
8. 删除时依据 `DELETE /videos/{id}` 的 `202` / `204` 区分“处理中”和“完成”；删除中只查询所属用户可见的 `/videos/{id}/deletion`，不再加载媒体、转写或总结。停止确认未就绪、工作目录/原视频清理失败时显示后端错误及可重试入口，只有进度接口或列表证明真正完成才移除记录。合法总结即使临时清理失败仍应可阅读，单独清理重试不触发模型请求。保留第 1～4 窗口既有 API 语义；只为页面闭环做必要、可验证的兼容性后端读模型调整。
9. 在 .scratch/mvp-stage-5/validation.md 记录前后端启动命令、浏览器源与代理目标、端口、截图或受限交互证据、真实接口请求状态、Range/播放跳转结果、测试命令、Docker 增量及限制；完成有意义阶段后更新既有产品与技术进度。真实成功任务可用于只读页面联调；若无法使用原验收账户，则用隔离账户和授权样本建立可重复场景，不修改第 4 窗口的成功结果或两条历史失配任务。测试生成的账户/视频仅按准确身份与确认停止的流程清理，不动业务用户资料。

非目标：

- 不重写任务生命周期、ASR/LLM、引用算法、冻结配置或数据库历史指纹；旧 `awaiting_summary` 来源失配的根因修复需要单独审查，不在页面窗口里靠降级校验或强制成功处理。
- 不实现分片上传、自动重试/接管、付费模型回退、非零起点媒体映射、公开部署、移动原生客户端或额外管理后台。
- 不恢复上传字节上限、业务目录容量硬限制、水位拒绝或写满拒绝测试；不迁移/清理其他 Docker 项目。

验收：

1. 前端类型检查、lint、构建和直接相关组件/状态测试通过；后端兼容改动有相应测试，完整适用后端测试及第 0 窗口回归继续通过。构建产物不含密钥、私密报告或真实转写。仅在改动范围内增加必要的依赖与构建缓存，并核对本项目 Docker 镜像、缓存、可写层和日志新增占用不超过 7 GiB；Stage 1/2 API、PostgreSQL/Redis、单 Worker 及既有数据保持健康。
2. 使用真实浏览器自动化（优先 Playwright）在同源入口验证注册→登录→原始流上传→列表/详情→提交→进度/转写→合法总结→引用跳转→退出/重新登录→删除/删除进度。可用隔离夹具确定性制造排队异常、恢复资格、清理失败、删除中和会话失效，随后用真实后端接口核对 UI；不能以静态假页面或仅通过单元测试冒充浏览器闭环。
3. 浏览器网络记录证明 `/api` 剥前缀、同源 Cookie 与 CSRF 正常，上传没有 multipart 包装，视频 HEAD/Range 经代理得到正确状态和长度；点击至少两条不同引用后，播放器实际跳到对应语音片段并继续播放，核对内容没有明显错位，不能只断言 `currentTime` 数字。验证未登录与另一账号无法读取视频、转写和总结，删除后新内容请求被拒绝；需要截图时遮蔽账号、原文、引文和任何私密信息。
4. 刷新详情页或重启前后端后，当前 task、attempt、合法总结和清理/删除状态仍从后端恢复；失败与清理并行状态不相互覆盖，重复点击恢复/续接不会创建多个有效 attempt。历史 `TRANSCRIPT_SOURCE_MISMATCH` 只显示稳定原因，不自动重复调用模型。已发布合法结果在临时清理失败时仍可阅读，单独清理重试不增加 ASR/LLM 请求。
5. 交付 React/TypeScript 页面、同源代理及本地运行说明、必要的最小后端读接口、自动化测试、.scratch/mvp-stage-5/validation.md、方案进度更新与逻辑提交哈希。结论只能依据实际验证称“第 5 窗口页面闭环通过”；第 6 阶段的最终展示材料、全流程复查与发布验收另行完成。

开始修改前及每次提交前检查工作区与暂存区，保护已有用户改动。先读取并运行直接相关的现有测试，再按可独立验收的小闭环推进，每个逻辑完整单元验证后按 Conventional Commits（英文类型、简洁中文描述）提交。不要提前实施第 6 阶段的展示包装或把浏览器状态当作 PostgreSQL 事实源。
